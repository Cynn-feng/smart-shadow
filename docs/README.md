这里是比赛完成后的持续开发文档入口。Agent 默认按 `00 → 01 → 02 → 03 → 04` 阅读：先看当前任务，再看决策、事实、技术方案和实施方案；随后按需查看市场/算法调研和验证记录。当前文档和研究切片可能尚未提交，开始任务前仍要运行 `git status --short`。

视觉算法已独立到 [`../../smart-shadow-vision-algorithm`](../../smart-shadow-vision-algorithm)；算法 Agent 应进入该目录并按其 `AGENTS.md → docs/00–04` 工作。这里的算法目录只作为兼容基线，主项目落地必须经过版本化 landing bundle。

## Agent 快速开始

每次接手任务先执行下面的顺序：

1. 在仓库根目录运行 `git status --short`，认领目标文件，保留其他 agent 的未提交改动。
2. 阅读 `AGENTS.md`，再按 `00-当前任务说明.md → 01-项目决策记录.md → 02-项目记忆.md → 03-技术方案.md → 04-实施方案.md` 建立当前边界。
3. 需要判断“是否已经验证”时查看 `07-验证与运行记录.md`；需要论文或市场依据时再查看 `05`、`06`。
4. 先把任务归入实施阶段，写明目标文件、接口/数据影响、验收命令和未完成边界，再开始改代码。
5. 轻量验证统一使用 `bash scripts/verify_lightweight.sh`；该命令通过也只代表契约、语法和合成回归层级。

任务登记必须同时写明唯一任务 ID、实施阶段、owner、独占文件、验收命令和回滚方式；交付时回写目标、改动、验收结果、已验证层级、仍未验证项和回滚方式。任务状态和文件占用以 [`active-tasks/README.md`](active-tasks/README.md) 为准，本文不复制任务清单。

## 四份核心项目文档

这四份文件是后续 Agent 的固定事实源，职责不要互相替代：

| 文件 | Agent 应该从这里得到什么 |
| --- | --- |
| `01-项目决策记录.md` | 已确认的边界、取舍、编号决策和暂缓事项；修改接口或结果含义前先更新这里 |
| `02-项目记忆.md` | 当前源码事实、验证层级、风险、阻塞项和未完成边界；不把假设写成事实 |
| `03-技术方案.md` | 目标架构、模块契约、数据字段、状态机、校准和可靠性约束 |
| `04-实施方案.md` | 阶段顺序、代码切片、依赖、验收命令、退出条件和回滚方式 |

任务说明回答“这轮先做什么”，决策记录回答“为什么这样做”，项目记忆回答“现在已经知道什么”，技术方案回答“系统应该怎样工作”，实施方案回答“下一步改什么并如何验收”。研究材料、运行记录和任务队列不能绕过这四份文档直接改变产品边界。

## 任务认领和阶段映射

开始修改前，把目标文件和实施阶段写在任务说明或交付记录中，避免多个 agent 同时改同一事实源：

| 任务类型 | 首选文件 | 实施阶段 | 先读内容 |
| --- | --- | --- | --- |
| 回执、错误语义、AI 响应校验 | `cm_client.go`、`server.go`、`contract/` | 阶段 1 | `01`、`03`、`04` |
| 会话、归属、上传安全 | `server.go`、`templates/`、迁移文件 | 阶段 2 | `01`、`03`、`04` |
| EvidenceV1、投影、outbox、索引恢复 | `server.go`、`cm_client.go`、`contract/` | 阶段 3 | `01`、`03`、`04` |
| 真实 manifest、检索/AIGC 评测 | `aigc/`、`eval/`、`tests/` | 阶段 4/7 | `01`、`02`、`03`、`06` |
| 启动、依赖、readiness、迁移和日志 | `start_all.sh`、部署配置 | 阶段 5 | `03`、`04`、`07` |
| 证据工作台和私有化 API | 先写决策，再改服务/UI | 阶段 6（暂缓） | `01`、`04`、`05`、`08` |

阶段 7 是可离线并行的算法研究线，不等于线上业务已进入阶段 6；阶段 6 必须等阶段 1–5 的验收门通过。若修改接口、字段、状态机、特征 schema 或结果含义，必须先在 `01` 和 `03` 记录，再进入代码。
